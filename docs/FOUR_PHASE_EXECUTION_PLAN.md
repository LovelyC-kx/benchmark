# 四阶段执行方案：先广泛发现，再形成论文

更新：2026-10-29；对应工程版本：0.4.0。

我们采用的顺序是：**广泛训练、完整留存与初析 → 原计划所有层级分析 → 深入发现、机制与理论链 → 根据实际发现组织论文并补实验。** 现在的任务是建立足够丰富、可以反复追问的实验世界。论文主张、最重要的图和贡献组合，由实际结果决定。

“全部”落实为两份总账：一份登记每个实验配置及其结果；另一份登记原计划每一节的分析要求、适用对象、实现和输出。原六层结构用于检查研究覆盖，论文最终可以采用更有解释力的组织方式。

## 1. 四个阶段怎样衔接

| 阶段 | 要完成的工作 | 交付物 | 转入下一阶段的依据 |
|---|---|---|---|
| 第一步：广泛全量跑 | 完整配置库、多种子、真实任务、模型参照；保存训练和分析材料；初析每个结果 | 训练总账、完整轨迹档案、逐场景预测/损失、初步现象目录、失败目录 | 已登记条件有完成结果或可处理的具体阻塞；全部结果进入初析 |
| 第二步：所有层级分析 | L1—L6、原文档的小节、数学控制、对应读出/干预/恢复及真实任务适配 | 逐小节覆盖表、拟合器和操作器、分析报告、跨条件图谱 | 原计划逐项有输出，或有具体的适用性判定及替代分析 |
| 第三步：深入研究 | 从现象建立竞争解释、决定性对照、跨条件规律、模型改进和理论联系 | 发现卡、证据链、反例、预测、新实验、设计收益 | 出现可以清楚解释并继续产生预测和改进的发现组合 |
| 第四步：形成论文 | 选择实际最强发现；确定核心问题、图序、贡献层次、相关工作和补实验 | 论文骨架、主图、完整方法与附录、公开复现实验包 | 论证连贯，关键预测与改进获得相应实验支持 |

第一步的训练与归档可以并行调度，初析随结果出现持续更新。第二步中已经成熟的公共分析也可提前执行；这里的先后关系规定研究重心和完成要求，不要求GPU在等待另一阶段时闲置。

## 2. 第一步：广泛全量跑

### 2.1 实验空间

保留原16任务、G01—G09、tagged内容/需求/年龄/写入世界、Binary Adding、Copy、MQAR，以及已登记的真实任务。分类、连续回归、序列分类、空间重建、多步真实预测各用自己的原生目标。原任务和新受控任务互相补充：前者提供连续性，后者帮助区分现象的来源。

模型包括12种参考单元、14种可注入参考骨架、18种连续参照，以及单列的作者原生模型轨道。兼容性由输入形状、目标、原生解码器与状态接口共同决定；新增有科学用途的典型模型继续进入来源总账和执行计划。

本次 `campaign-plan` 对扩展模型名单计算的合成配置数如下。均为五个种子11、22、33、44、55；未加入真实数据，尚未跨profile去重。

| 配置族 | 每seed配置数 | 五seed配置数 | 主要展开方向 |
|---|---:|---:|---|
| full | 63,054 | 315,270 | 全任务库、内容、需求、负荷、年龄、版本、写入、能量、频率、采样 |
| paired | 25,042 | 125,210 | 单元机制、观察相位、读出及配对对照 |
| learning | 16,858 | 84,290 | 前向状态与时间信用、SG、reset梯度、编码等 |

这些数字表示当前可编译设计的规模。加入真实canonical数据后，编译器按实际兼容模型增加配置；队列记录实际唯一run数。来源总账还保留尚未下载、尚需转换和作者环境尚需接通的项目，使后续补齐有明确位置。

已有参考模型与作者代码的对应见[模型与数据扩展](REAL_DATA_AND_MODEL_EXPANSION.md)、[近期benchmark复核](BENCHMARK_REVIEW_2025_2026.md)。作者原生轨道需要固定原仓库、数据协议、训练命令和结果读取，再与统一轨道建立映射。

### 2.2 覆盖、训练预算与结果保留

所有已登记配置进入全量队列。工程短验收负责发现形状、显存、读写和恢复问题；其分数不用于删除不讨喜的模型。训练不足、静默、过度发放、发散、对历史敏感、性能较差及条件翻转，均进入结果目录。

固定宽度/深度、等参数、等运行状态和等训练计算回答不同问题，分别建立预算表。第一轮给出共同训练协议的完整图景；验证集上的学习率、增益、阈值、衰减、初始化和预算追加有单独版本。发现训练不足时增加明确的延长训练条件，保留原预算结果，从而研究能力与可训练性的差别。

每个配置保存初始、指定更新比例、best和last检查点。训练曲线、参数变化、工作点变化和表征形成可以共同读取。后续需要更密的形成过程时，从已有进度重放并新增采样，而不丢掉原始实验。

### 2.3 84GB显存怎样使用

资源规划采用用户提供的每卡84GB。`doctor`和`campaign-plan`在服务器读取实际可见设备、总字节、当前空闲显存及磁盘空间，并保存硬件清单。实际GPU数量由服务器检测，命令中的编号使用现有可见设备的逻辑编号。

初始每GPU一个训练进程。按向量、长序列attention、卷积、空间重建、真实预测分别实测训练峰值、采集峰值、单步耗时、CPU内存与落盘吞吐。先以实际显存的80%作为规划预算，给优化器、梯度、分析和运行波动留空间；这不是自动改变训练batch的规则。根据吞吐测量再安排小模型并发，训练与归档使用各自队列。

归档batch可以因显存调整；它只改变采集分块，场景数量与坐标维数保持不变。训练batch属于优化条件，改变时产生新的实验身份。当前入口支持单机多GPU独立任务和Slurm分片；AMP、编译、分布式训练等加速另设执行版本并实测结果。

### 2.4 必须留下哪些内容

| 材料 | 保存内容 | 后续用途 | 当前入口 |
|---|---|---|---|
| 数据与任务世界 | 原始来源、canonical manifest与校验；生成器版本、种子、scene/source/group ID、角色、目标与潜变量 | 原场景重建、真实来源追踪、成对实验 | data、prepare、source_roster |
| 配置与环境 | task/model/train/analysis合同，源码SHA、软件/设备/数值开关，实际配置和阻塞原因 | 确定比较条件、重放和迁移 | spec、checkpoint、environment |
| 训练检查点 | 全权重、优化器、RNG、样本顺序/游标、更新数、最佳验证值 | 中断续跑、学习过程和追加训练 | step_*.pt、best.pt、last.pt |
| 每次优化更新 | 样本索引/ID、逐场景原生损失与correct、LR、裁剪前梯度范数、裁剪后各参数梯度统计、耗时与CUDA峰值 | 训练稳定性、有效更新、困难样本与失败定位 | updates.jsonl |
| 完整分析轨迹 | 固定分析场景库每一步、每个状态owner的全部状态/诊断项，全部叶子模块输入输出，cache、读出累计与流游标 | 内容、载体、时间、路径、干预及后缀重放 | archive/下完整坐标ZIP分片 |
| 原生结果 | 完整预测、完整目标、合法mask、逐场景风险、准确率/预测指标 | 重新分组、重建误差分析和现象定位 | archive、native_outputs.npz |
| 分析拟合结果 | 当前已接通的线性/非线性读出权重、标准化、实际投影、几何拟合及时间transport参数 | 检查“读到了什么”、迁移、复用和重算 | fitted_readers/及SHA目录 |
| 未完成与失败 | 异常阶段、实际batch、前后RNG、权重/优化器现场、部分归档、未提交日志尾部 | 失败现象研究、修复和可追踪重试 | failure_update、failed ZIP、uncommitted日志 |

**完整归档的单位**是“固定分析场景库 × 所有保存的检查点 × 每个输入时步 × 所有注册状态/叶子模块输出”。保存原始tensor精度和全部坐标，二值位压缩、内容去重和不变KV前缀复用只改变编码方式。用于快速拟合的128坐标缓存继续单列；完整档案不受这个限制。

默认完整场景库包括calibration、probe_train、probe_val、verification_train、verification_val、development，数量随分析合同登记；默认参数共1,920场景/检查点。confirmation和audit在相应研究阶段显式采集。所有训练batch的激活不常驻归档；逐更新日志、确定性场景、检查点和RNG支持按需要重放，再采集梯度张量、Jacobian、特定模块内部量等额外材料。后续专用拟合器和操作器接入时，同样保存其参数和权限合同。

### 2.5 存储与吞吐也是第一步的交付物

在每种实际形状上测量：检查点字节、完整轨迹逻辑字节/编码后字节、每场景归档耗时、模块数与时间长度、每次训练更新和分析耗时。使用实际唯一run数和保存进度数汇总：

$$B_{\rm total}=\sum_r\left[B_{\rm data,r}+B_{\rm journal,r}+\sum_c B_{\rm checkpoint,r,c}+\sum_{c,s}B_{\rm archive,r,c,s}+B_{\rm analysis,r}\right].$$

数据世界共享计一次；不同checkpoint和分析版本分别计。attention的不可变KV前缀采用精确增量引用，避免同一前缀在每步重复存整个副本。空间叶子输出仍可能占大头，应实测完整档案再配置落盘节点和容量。分片校验、原子写入、已完成分片复用和队列恢复已接通，可以分批执行全部配置而保持材料连续。

### 2.6 第一轮初析看什么

每个结果首先有原生风险/准确率、逐场景分布、训练曲线、参数更新和工作点。配合current/recent/unordered/ordered观察参照，回答“这份输入中历史到底提供什么”。按任务轴、模型、单元、观察相位、读出、种子、来源组和训练进度生成切片。

初步发现目录同时登记：优势、退化、无变化、负效应、排名翻转、异常失败、训练转折、同分不同内部过程。它负责给第二、三步提供定位线索，所有条件仍进入对应层级分析。

## 3. 第二步：把原计划的所有分析逐项做完

### 3.1 原计划总账怎样读取

`coverage.plan_inventory`扫描原Master、根目录研究文档和六份规范coverage图。目前得到40个主模块、29个明确编号细分节、33份来源文档和907个标题索引。907是检索上下文数量；主模块和细分节用独立命名空间，避免不同阶段的编号重名。

生成的 `all_layer_coverage.json` 为每项保留原文路径、SHA、执行逻辑、代码候选和共享runner映射。完成一项时应连接：适用任务/模型、拟合/选择/评价角色、checkpoint SHA、具体输出、失败/不适用原因和后续问题。

现有14个公共模块提供共享计算：task_controls、working_point、mechanism、probes、geometry、temporal、communication、access、selective、interventions、recovery、reconstruction、anova、theory。`all_shared`队列负责执行这14项；原计划的专用控制逐项迁移后共同构成第二步的完整结果。

### 3.2 六层分别要回答什么

| 层 | 全面分析的核心 | 需要连接的证据 | 深入时可产生的新问题 |
|---|---|---|---|
| L1：任务与需求 | 哪种内容、时间、版本、顺序、频率或证据是答案所需 | 观察参照、同观测异目标配对、解析参照、真实来源与目标合同 | 现有benchmark测到了哪种能力？新设置能区分哪些隐藏差异？ |
| L2：动态与实现 | 衰减、发放、reset、辅助状态、递归和工作点怎样改变处理 | 逐步电流账、完整状态、单元配对、路径/事件干预、参数与状态预算 | 相同表面结构为何实现不同记忆？哪些单元/骨架组合形成特殊处理区间？ |
| L3：表征与传递 | 保留什么、存在哪里、怎样组织、何时可读、如何传递 | 线性/非线性探针、联合分解、角色几何、非线性交互、时域迁移、消息操作 | 保留量相同而功能不同的原因？表征重组、协同与冗余怎样变化？ |
| L4：读取、使用与恢复 | 原下游究竟使用了什么，局部改变如何影响最终功能 | 权限/摘要/读出对照、潜空间/任务度量、选择操作、路径干预、四风险恢复、空间分区 | 可读而未用的内容怎样转为有效收益？历史何时帮助、干扰或能够修复？ |
| L5：跨条件与指导意义 | 规律怎样跨负荷、时间、模型、真实模态与预算迁移 | 分布外条件、负荷/时间曲面、未见条件预测、结构改动、系统资源 | 哪些诊断可以预测改动收益、失效边界和模型选择？ |
| L6：学习与形成 | 状态能力如何在优化中形成；前向动态和信用怎样相互作用 | 全进度检查点、梯度统计、SG/reset梯度对照、初始化/课程/预算、表征形成 | 结构潜力与实际可学习性如何分离？怎样改善训练并形成目标机制？ |

L5、L6从第一步就有实验和数据准备，第二步按原计划开展分析。其后续深入问题与第三步相连，不能因它们需要实际结果而从覆盖表中消失。

### 3.3 专用内容的接入顺序

先固定单项合同和参考计算，再接真实已训练检查点；保留原文献代码/公式与适配位置。每次接入都输出该项的数值控制、作用对象和拟合器/操作器，并把结果回写总账。

1. **内容、几何与理论**：独立副本/秩选择、角色支撑、完整交叉项、非线性产品世界、潜空间与任务谱、Gaussian参照及真实网络偏离。
2. **载体、时间与通信**：完整辅助状态/cache的载体集合搜索，不规则时钟，所有实际消息消费路径，局部与联合操作及匹配对照。
3. **读取与恢复**：读出族/预算、任务条件化潜空间、选择操作、四组风险、方向性和多owner恢复；分类、回归、空间目标分别适配。
4. **真实与跨条件**：原生来源/运动/配准/时间分辨率、区域与频率、有效/过时历史、域与负荷迁移、未见条件预测和模型改动。
5. **学习与资源**：前向相同而反向不同的配对、逐进度表征与梯度关系、初始化/课程/预算、实际GPU/系统测量和相应作者原生轨道。

这是一份实施顺序，保留各项原要求。遇到原方法假设与任务不匹配时，构造适配实验、对照或新的分析方式；原方法的边界本身也可能产生值得研究的发现。

## 4. 第三步：从现象到机制、理论和可指导设计

### 4.1 一条发现如何深入

每条发现建立独立记录：观察及条件 → 涉及run/checkpoint/场景 → 竞争解释 → 能区分解释的实验 → 机制结果 → 可外推预测 → 模型/读出/指标改进 → 新条件验证。目录允许一条现象分叉为多种解释，也允许若干现象合并为共同规律。

具体工作包括：

1. 从全图谱中定位效应和转折，查看个体种子、逐场景和中间过程。
2. 找到最能形成对照的病例：同风险不同表征、同保留不同使用、同几何不同功能、同前向不同学习、同单元不同骨架。
3. 区分内容缺失、表示纠缠、载体错置、时间错配、读出不适配、消息利用不足和历史干扰；允许联合原因。
4. 通过状态/消息/边/读出操作与恢复形成更强证据，再看改变结构、训练或读取方式能否产生预计收益。
5. 在别的时间长度、负荷、任务、真实数据和模型上验证预测；失败时研究失效边界与反例。
6. 把可解析局部模型、精确恒等式、概率/动力系统分析与深网络观测连接。适用时推导界、近似、缩放关系或相变条件，并用实验检查。

### 4.2 值得主动追踪的发现路线

| 路线 | 关键问题 | 可追加的实验/分析 | 可能形成的成果 |
|---|---|---|---|
| 保留—读取—使用—干扰 | 更多历史为什么有时无益或有害？ | 内容配对、读出权限、选择擦除、路径操作与恢复 | 系统能力分解、有效记忆指标、结构/读出设计 |
| 时间与负荷转折 | 失效是渐变还是突然发生？由什么共同决定？ | 年龄×写入×需求×宽度曲面、状态/频谱/梯度轨迹 | 工作区间、容量规律、临界条件与预算设计 |
| 角色与几何重组 | 同一内容何时从有用变成干扰？ | 改目标但固定输入，联合子空间、任务度量和读出迁移 | 任务条件化表征规律、读出适配或内容保护机制 |
| 多载体与多路径 | 单点探针/干预为什么遗漏功能？ | 状态集合、辅助载体、cache与消息联合操作，多owner恢复 | 协同/冗余图谱、更合适的单元和骨架接口 |
| 时间表征变化 | 内容是在消失、转向、换编码还是移到别处？ | train-time×test-time矩阵、transport、联合载体探针和解码器重拟合 | 读出对齐、时间适配、稳定性与可塑性设计 |
| 学习形成 | 可存储的系统为何未学会利用？ | 同前向反向配对、训练进度、SG/初始化/课程改动 | 可训练性机制、训练策略与动态参数设计 |
| 跨真实任务迁移 | 受控世界中的诊断能预测真实收益吗？ | 真实来源切片、自然/人工时间扰动、未见条件预测 | 实用诊断、模型选择、新任务和跨模态规律 |
| 意外失败与反例 | 哪些结果推翻了我们的直觉？ | 保留失败现场、简化重现、竞争模型、构造反例 | 新机制解释、指标修正、新benchmark设置 |

这些是发现方向，允许新增和改写。新的设置、配对、测量方式、分析工具、规律、理论解释和有效模型改动，都可以成为贡献。对已有思想和代码的复用保持清楚来源，并继续通过组合、适配和深入分析创造新的解释力和指导价值。

### 4.3 结果读取方式

首先建立完整现象目录，再由问题驱动查看切片和个例。每张汇总图能下钻到配置、checkpoint、场景、原始预测、完整状态和拟合器。跨seed检查稳定性，真实数据按父来源组查看；同时保留方向相反的条件和足够明确的反例。

已形成的候选解释在新数据或新条件上作出具体预测。探索过程中可以广泛产生假设，确认阶段再按实际问题组织独立检验；保留探索与确认的版本关系，便于知道一个发现如何成长。

## 5. 第四步：让实际发现决定论文

此时再选择主线，例如“什么条件决定有效历史”“表征与使用为什么分离”“一个能预测设计收益的统一诊断”等；这些只是候选，结果可以带来更好的问题。

论文的图序优先形成一条读者能跟随的逻辑：重要现象 → 现有判断遗漏什么 → 新分析如何区分 → 机制解释 → 可预测的新条件 → 模型/训练/读取改进及真实收益。主文保留最有力量的发现和必要方法，六层全覆盖资料为方法、扩展实验和可复用资源提供支撑。

补实验由论证中实际缺少的连接决定：更多任务、作者原生模型、更宽资源范围、额外理论、构造反例或更强改进。新增工作有版本并回接原总账，形成持续迭代的研究资产。

## 6. 现在可以执行的命令

完整安装、数据下载/转换与多节点细节见[服务器手册](SERVER_RUNBOOK.md)。以下示例在仓库根目录执行；真实数据路径换为已经verify的canonical根目录。

```bash
python -m snnbench doctor

# 仅生成设计、硬件与覆盖清单，不启动训练。
python -m snnbench campaign-plan --root /data/snn/campaign_v04 \
  --profiles full paired learning --seeds 11 22 33 44 55 \
  --archives /data/snn/canonical/har /data/snn/canonical/shd

# 完成工程短验收后，物化全部配置并进入同一个去重队列。
python -m snnbench campaign-plan --root /data/snn/campaign_v04 \
  --profiles full paired learning --seeds 11 22 33 44 55 \
  --archives /data/snn/canonical/har /data/snn/canonical/shd --materialize

python scripts/launch_local_gpus.py --gpus 0 1 2 3 \
  --db /data/snn/campaign_v04/train.sqlite \
  --runs /data/snn/campaign_v04/runs --data /data/snn/campaign_v04/data

# 将目前已完成模型的所有保存进度加入完整归档与初析队列。
# 后续再次运行会补进新完成的模型，不重复已有工作。
python -m snnbench campaign-stage --root /data/snn/campaign_v04 \
  --phase preliminary --checkpoints all --archive-batch 8
python -m snnbench post-worker \
  --db /data/snn/campaign_v04/post_preliminary.sqlite --device cuda:0

python -m snnbench summarize --runs /data/snn/campaign_v04/runs \
  --out /data/snn/campaign_v04/results_stage1

# 第二步先执行全部14项共享分析，随后逐项完成原计划专用分析。
python -m snnbench campaign-stage --root /data/snn/campaign_v04 \
  --phase all_shared --checkpoints all
python -m snnbench post-worker \
  --db /data/snn/campaign_v04/post_all_shared.sqlite --device cuda:0
```

有几张可用卡就使用对应逻辑编号；训练和后处理进程按资源分配，以上两组worker不必同时占用同一张卡。SQLite放单主机本地盘；跨节点用独立队列分片。post-worker处理当前已入队工作后退出，新增工作可再次启动。

单模型的完整归档入口：

```bash
python -m snnbench archive --run /data/snn/campaign_v04/runs/RUN_ID \
  --data /data/snn/campaign_v04/data --checkpoint step_00000000.pt \
  --device cuda:0 --batch-size 8
```

正式全量归档使用合同中的全部场景。`--scenes`可显式用于工程测量；`--owners-only`用于只采状态的专项实验；二者的实际范围会写入合同。快速分析的`--batch-size`、`--max-features`、`--max-targets`已暴露为CLI参数，增加分析预算会生成独立分析身份。
